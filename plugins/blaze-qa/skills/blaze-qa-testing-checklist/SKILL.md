# Testing Checklist — შემოწმების სია

## აღწერა

blazeteam-ის Jira სთორებისთვის Testing Checklist-ის ავტომატური გენერაცია.
სთორის შინაარსის ანალიზის საფუძველზე ქმნის სტანდარტულ + ტასკ-სპეციფიკურ
შემოწმების სიას, მზადს Jira-ს `Testing Checklist` ველში ჩასასვლელად.

## ამოქმედება

გამოიყენება როდესაც:
- მომხმარებელი იყენებს `/qa-checklist` ბრძანებას
- მომხმარებელი ითხოვს ტასკის Testing Checklist-ს

---

## ფორმატის წესები (სავალდებულო)

Jira-ს `Testing Checklist` ველი ჩვეულებრივი rich text (ADF) რედაქტორია.
ფორმატი შერჩეულია ისე, რომ პირდაპირი copy-paste სუფთად ჩაჯდეს:

- checklist-ის თითო პუნქტი იწერება **უბრალო bullet-ით**: `- პუნქტი`
  (დეფისი + space + ტექსტი). paste-ისას ADF სუფთა bullet-სიად აქცევს.
  ⚠️ **არ გამოიყენო** `- [ ]` ან `[]` (ოთხკუთხა ფრჩხილები) — ADF მათ
  ლიტერალურ ტექსტად ან „not done"-ად ტოვებს.
- სექციის სათაური იწერება `### სათაური` ფორმატით (ADF-ში heading-ად ჩაჯდება).
- **Out of Scope სექცია ჩექლისტში არ ემატება.** Out-of-Scope ფუნქციონალი
  უბრალოდ არ შედის შემოწმების სიაში.
- **„დასაზუსტებელია" სექცია არ ემატება.** დაუზუსტებელი პუნქტი, თუ
  რელევანტურია, ჩვეულებრივ checklist პუნქტად ჩაიწერება Functional Testing-ში.

## სამუშაო პროცესი

**ნაბიჯი 1 — წაიკითხე ტასკი**
`getJiraIssue` (cloudId: `46d13e6c-fdcd-4cba-8837-fd7bc666b608`, `fields: ["*all"]`).
გამოიყენე `responseContentFormat: "markdown"`.
წაიკითხე: summary, description, acceptance criteria, კომენტარები, subtask-ები,
issue type, `customfield_10113` (Testing Checklist — არსებული შევსება, თუ გამოდის).

**ნაბიჯი 2 — გაანალიზე ტასკი**
განსაზღვრე:
- რომელი **სტანდარტული სექციები** გამოიყენება (იხ. სექციების ლოგიკა)
- რომელი **ტასკ-სპეციფიკური პუნქტები** ემატება (იხ. სპეციფიკური სიგნალები)

Out-of-Scope ფუნქციონალი უბრალოდ გამოტოვე — ჩექლისტში არ ჩართო.
ცალკე „დასაზუსტებელია" სექცია არ დაამატო.

**ნაბიჯი 3 — დააგენერირე ჩექლისთი**
შაბლონის მიხედვით, სტანდარტული + სპეციფიკური პუნქტების კომბინაციით,
bullet ფორმატით (`- პუნქტი`).

**ნაბიჯი 4 — გამოიტანე შედეგი**
მზა ტექსტი Jira Testing Checklist ველისთვის (copy-paste ფორმატი).

## ჩექლისთის სტანდარტული შაბლონი

### Requirement / Task Review (მოთხოვნების გადახედვა)
- ტასკის აღწერა გასაგებია
- Acceptance Criteria (მიღების კრიტერიუმები) არსებობს
- გაურკვეველი საკითხები დაზუსტებულია
- დიზაინი / მაკეტი გადახედილია

### Functional Testing (ფუნქციური შემოწმება)
- ფუნქციონალი მუშაობს (happy path — წარმატებული სცენარი)
- სავალდებულო ველები მოწმდება
- ცარიელი ველების ქეისი (negative — უარყოფითი სცენარი)
- არასწორი მონაცემების ქეისი (negative — უარყოფითი სცენარი)
- მონაცემის შენახვა / განახლება სწორია
- წაშლის შემოწმება
- სტატუსის ცვლილების შემოწმება
- ფილტრაციის შემოწმება
- ძებნის შემოწმება
- სინქრონიზაცია მუშაობს (არსებობის შემთხვევაში)
- შეტყობინებები (Success / Error — წარმატება / შეცდომა) სწორია
- ლოგირება თითოეულ ქმედებებზე მოწმდება

### UI / UX Basic Checks (ინტერფეისის ძირითადი შემოწმება)
- ელემენტები სწორად ჩანს
- ტექსტები არ არის გაწყვეტილი
- ღილაკები აქტიური / არააქტიური სწორად მუშაობს
- Placeholder / Label სწორია
- Responsive (ადაპტური გამოჩენა) შემოწმებულია
- სხვადასხვა მოწყობილობაზე შემოწმებულია (აპლიკაციების შემთხვევაში)

### Data & Logic Validation (მონაცემებისა და ლოგიკის ვალიდაცია)
- მონაცემი სწორად ინახება
- Refresh (გვერდის განახლება) შემდეგ მონაცემი არ იკარგება
- Duplicate (დუბლიკატი) ჩანაწერები სწორად მუშავდება
- ბიზნეს ლოგიკა დაცულია

### API / Backend
- სწორი Request (მოთხოვნა) იგზავნება
- სტატუს კოდი შეესაბამება ქეისს
- Error response (შეცდომის პასუხი) სწორია
- Response structure (პასუხის სტრუქტურა) სწორია

### Permissions / Roles (უფლებები / როლები)
- სწორი როლი ხედავს ფუნქციონალს
- არასწორი როლი შეზღუდულია
- Access denied (წვდომა აკრძალულია) ქეისები მოწმდება

### Regression (რეგრესია)
- მოქმედებს თუ არა სხვა ფუნქციონალზე
- ძირითადი regression checklist (შემოწმების სია) გავლილია
- ცვლილება არ არღვევს არსებულ ფუნქციებს

### Final Checks (საბოლოო შემოწმება)
- ბაგები დაფიქსირებულია Jira-ში (არსებობის შემთხვევაში)
- Test Case-ები განახლებულია
- სტატუსი განახლებულია Jira-ში

## ტასკ-სპეციფიკური სიგნალები და დამატებითი პუნქტები

სთორის შინაარსის ანალიზისას, ქვემოთ მოცემული სიგნალების შემთხვევაში
შესაბამისი პუნქტები ემატება **Functional Testing** სექციაში:

### გარე სერვისის ინტეგრაცია (SDA, eFlow, EMIS და სხვ.)
სიგნალი: სთორი ახსენებს გარე სერვისს, API-ს ან გადამოწმებას
- (სერვისი) — წარმატებული გადამოწმება / ინტეგრაცია (positive — დადებითი სცენარი)
- (სერვისი) — მონაცემი ნაწილობრივ ნაპოვნია / გამაფრთხილებელი მდგომარეობა
- (სერვისი) — სერვისი მიუწვდომელია / შეცდომის დამუშავება (negative — უარყოფითი სცენარი)
- (სერვისი) — მონაცემი არ მოიძებნა (negative — უარყოფითი სცენარი)

### კოდის / ID-ის ავტომატური გენერაცია
სიგნალი: სთორი ახსენებს კოდის, ID-ის ან ნომრის ავტომატურ შექმნას
- კოდი / ID ავტომატურად გენერირდება
- გენერირებული კოდი სწორი ფორმატისაა
- კოდი არ მეორდება გაუქმების შემდეგ

### ადმინისტრირების / რედაქტირების ვადა
სიგნალი: სთორი ახსენებს ვადებს, პერიოდებს ან „ადმინისტრირებისთვის გამოყოფილ დროს"
- ვადის ფარგლებში — ფუნქციონალი ხელმისაწვდომია (positive — დადებითი სცენარი)
- ვადის გარეთ — ფუნქციონალი დაბლოკილია, შეცდომის შეტყობინება სწორია (negative — უარყოფითი სცენარი)
- ინდივიდუალური ვადა (კონკრეტული ინსტიტუციისთვის) სწორად მუშაობს

### უნიკალურობის შემოწმება
სიგნალი: სთორი ახსენებს უნიკალურობას, დუბლირებას ან კომბინაციების შეზღუდვას
- დუბლიკატი — იმავე კომბინაციით ჩანაწერი უარიყოფა (negative — უარყოფითი სცენარი)
- გაუქმებული სტატუსი — უნიკალურობის გარეთ (negative — უარყოფითი სცენარი)
- სხვადასხვა სასწავლო წელი — ერთი და იგივე კომბინაცია დაიშვება

### სტატუსის მატრიცა
სიგნალი: სთორი ახსენებს სტატუსების ცვლილების წესებს
- დაშვებული გადასვლა: სტატუსი A -> სტატუსი B (positive — დადებითი სცენარი)
- დაუშვებელი გადასვლა: სტატუსი A -> სტატუსი B (negative — უარყოფითი სცენარი)
- გაუქმება — მხოლოდ განაწილების გარეშე (negative — უარყოფითი სცენარი)

### წინა სასწავლო წლის ასლი / კოპირება
სიგნალი: სთორი ახსენებს ასლის შექმნას, კოპირებას ან წინა წლის მონაცემების გადატანას
- ასლი იქმნება სწორი ველებით (ავტომატური ველები არ გადადის)
- ახალ ჩანაწერს ახალი კოდი მიენიჭება
- ასლის ხელახლა შექმნა — შეცდომის შეტყობინება (negative — უარყოფითი სცენარი)

### ფაილების ატვირთვა
სიგნალი: სთორი ახსენებს ფაილებს, attachment-ს ან დოკუმენტაციას
- დასაშვები ფორმატი — ატვირთვა წარმატებულია (positive — დადებითი სცენარი)
- დაუშვებელი ფორმატი (negative — უარყოფითი სცენარი)
- ზომის ლიმიტის გადამეტება (negative — უარყოფითი სცენარი)
- ჩამოტვირთვა სწორად მუშაობს

### ცვლილებების ისტორია
სიგნალი: სთორი ახსენებს ისტორიას, audit log-ს ან ცვლილებების აღრიცხვას
- ისტორია ივსება ავტომატურად
- ისტორიაში ჩანს: მომხმარებელი, ცვლილება, თარიღი
- ისტორია read-only (მხოლოდ წასაკითხი) — რედაქტირება შეუძლებელია

### გლობალური სვიჩერი / კონტექსტი
სიგნალი: სთორი ახსენებს სვიჩერს, სკოლის / RC-ის კონტექსტს
- სვიჩერში სკოლა — სკოლის ფუნქციონალი ხელმისაწვდომია
- სვიჩერში RC — RC-ის ფუნქციონალი ხელმისაწვდომია
- სვიჩერის ცვლილებისას კონტექსტი განახლდება

### eFlow ინტეგრაცია
