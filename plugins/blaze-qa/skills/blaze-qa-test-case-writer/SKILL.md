# blazeteam QA — ტესტ-ქეისების წერა

> გამოსავალი ფორმატი: Qase.io JSON იმპორტი. მუშაობს ნებისმიერ blazeteam პროდუქტზე.

## ამოქმედება

- მომხმარებელი ითხოვს blazeteam-ის Jira სთორიზე ტესტ-ქეისების დაწერას
- გამოიყენება `/qa-test-planner` ბრძანება

## პროდუქტ-სპეციფიკური კონფიგი (მიმდინარე პროექტის CLAUDE.md-იდან)

ეს სქილი კომპანია-wide-ია. თითო პროდუქტისთვის ცვალებადი პარამეტრები
აიღება **მიმდინარე პროექტის `CLAUDE.md`-იდან**; თუ იქ არ არის — დააზუსტე:

- **suite root** — პროდუქტის სახელი (მაგ. `Eschool`)
- **Out of Scope** — პროდუქტ-სპეციფიკური გამონაკლისები
- **output დირექტორია** — სად ინახება JSON

## სამუშაო პროცესი

**ნაბიჯი 1 — წაიკითხე სთორი**
Jira issue-ს სრული აღწერა + ყველა კომენტარი. კომენტარი სჯობს აღწერას წინააღმდეგობის შემთხვევაში.

**ნაბიჯი 2 — აღმოაჩინე კონტექსტი**
შეამოწმე დალინკული სთორები (`issuelinks` + smartlinks) და დიზაინის ლინკები (Figma, სქრინშოთი). ჩამოთვალე ნაპოვნი ლინკები და **ნებართვის შემდეგ** გააანალიზე.

**ნაბიჯი 3 — Out of Scope ამოიღე**
სთორიში + პროექტის CLAUDE.md-ში Out of Scope-ად მონიშნული ფუნქციონალი არ ტესტირდება. (→ `rules/coverage.md`)

**ნაბიჯი 4 — გეგმა წარადგინე**
ფაილის გენერაციამდე ცხრილის სახით: ჯგუფები, ქეისების რაოდენობა (pos/neg), suite სახელი, Out-of-Scope გადაწყვეტილებები. **დაელოდე დამტკიცებას.**

**ნაბიჯი 5 — დააგენერირე JSON**
მხოლოდ დამტკიცების შემდეგ. გამოიყენე Node.js შაბლონი. (→ `rules/format.md`)

**ნაბიჯი 6 — ვალიდაცია**
ტექნიკური + შინაარსობრივი გადამოწმება. (→ `rules/validation.md`)

## Jira

`getJiraIssue` (`blazeteam.atlassian.net`, cloudId: `getAccessibleAtlassianResources`-ით).
დალინკული სთორის ინფო — მხოლოდ მთავარი სთორის საზღვრების გასაზუსტებლად, არასოდეს მისთვის ქეისების გენერირებისთვის.

**დიზაინი:** Figma ლინკი — `web_fetch` / ბრაუზერით; სქრინშოთი — პირდაპირ `Read`-ით.

## წესები (ამ სქილთან ერთად ჩალაგებული)

- `rules/format.md` — Qase.io JSON სქემა + Node.js გენერატორი
- `rules/content.md` — სათაური, წინაპირობა, ნაბიჯები (ქართული „ჩვენ"-ფორმა)
- `rules/coverage.md` — 12 სავალდებულო ჯგუფი + სიის გვერდის edge cases + Out of Scope
- `rules/heuristics.md` — Priority / Severity / Behavior
- `rules/validation.md` — გენერაციის შემდგომი ტექნიკური + შინაარსობრივი შემოწმება
